인증 구현 설명서

① 무엇으로 붙였나

Supabase Auth(이메일+비밀번호), @supabase/supabase-js@2.112.4.

② 왜 그걸 골랐나

이미 Supabase Postgres + Row Level Security 위에서 이 앱이 동작 중이라 auth.uid()로 바로 연결된다. 검토했으나 고르지 않은 방법:

  • 직접 구현(bcrypt+JWT) — 세션 무효화·토큰 재발급 등 보안 디테일을 직접 구현·검증하는 부담이 큼
  • 별도 인증 서비스(Auth0/Clerk) — 인프라가 하나 더 늘고 DB RLS와의 연동 지점이 늘어남

③ 어디를 어떻게 고쳤나

  • 가입: #signup-form → pds-auth.js → pds-app.js(Auth.signUp) → POST /auth/v1/signup → auth.users에 계정 생성(비밀번호는 bcrypt 해시로 저장)
  • 로그인: #login-form → pds-auth.js → Auth.signIn → POST /auth/v1/token?grant_type=password → JWT access/refresh token 발급
  • 로그아웃: #logout-btn → Auth.signOut → POST /auth/v1/logout → 세션 사라짐을 감지해 로그인 화면으로 복귀
  • 자료 조회: pds-ui.js의 refreshPlans() → Plans.list → PostgREST가 요청 JWT의 auth.uid()로 plans_select 정책(using (user_id = auth.uid()))을 적용해 내 자료만 반환

DB 쪽: supabase/migration-t07-auth.sql로 기존 T06 데이터를 보존한 채 5개 표 (plans/plan_revisions/todos/execution_logs/retrospective_notes) 전부에 user_id 컬럼을 추가하고 RLS를 authenticated + user_id = auth.uid() 기준으로 재작성했다. anon 롤에는 이 5개 표 어떤 권한도 남기지 않았다.

④ 안 열리는 것을 확인한 기록

anon key만으로 라이브 프로젝트에 curl로 직접 요청을 보내 확인(일회용 테스트 계정 사용, 비밀번호는 어디에도 남기지 않음). 아래는 실제 관측된 상태 코드다.

⑤ AI와 나

인증 방식은 AI가 Supabase Auth를 추천했고 내가 최종 승인했다. RLS 마이그레이션 SQL과 로그인 게이트 코드는 AI가 작성했지만, 대시보드에서 단계별로 실제 실행한 것과 실계정 생성·데이터 이관 확인은 내가 직접 했다. 카드 2~4의 거절 근거는 AI가 라이브 프로젝트에 curl로 요청을 보내 모았고, 예상과 다른 관측이 나왔을 때 문장을 고쳐 덮는 대신 원인을 규명해 ⑥에 그대로 남기게 했다. 5일 로그의 질문·지표·계산 규칙은 내가 정했고 기록도 직접 입력했다.

⑥ 아직 못 막은 것

  • 로그아웃·비밀번호 변경·계정 삭제 중 무엇을 해도, 그 전에 발급된 access token(JWT)은 자연 만료(최대 1시간) 전까지 계속 통한다. refresh token과 계정 자체는 즉시 무효화되지만, access token은 서명·만료만으로 자체 검증되는 무상태 토큰이라 서버가 개별 취소를 기억하지 않기 때문이다. 토큰이 탈취되면 최대 1시간의 위험 구간이 남는다. 완화책은 짧은 만료(1시간)뿐이고, 서버 쪽 토큰 블랙리스트나 세션 버전 관리는 붙이지 않았다.
  • 남의 행 수정·삭제 시도가 항상 명시적 403은 아니다 — 경우에 따라 “조용한 무효 처리”(200+빈 배열)로 응답한다. 원인: Postgres RLS는 UPDATE/DELETE 대상 행을 찾을 때 그 표의 SELECT 정책도 함께 적용하므로, 애초에 SELECT를 통과 못 하는 남의 행은 대상 후보로도 안 보인다. 데이터는 안전하지만 응답 형태가 균일하지 않다.
  • 무차별 대입(brute-force) 로그인 시도 횟수 제한을 이 앱이 직접 만들지 않았다 — Supabase Auth 자체의 기본 rate limit에 의존한다.
  • 비밀번호 재설정 메일의 링크 클릭은 실제로 밟아보지 못했다 — 기능·화면 전환은 확인했으나 메일함 접근이 안 됐다.

카드 1~4 · 증거 요약

카드 1 — 무엇으로 붙일지 고르고, 이유를 적기

Supabase Auth(이메일+비밀번호), @supabase/supabase-js@2.112.4. 고르지 않은 방법과 이유는 설명서 ②. 가입 200 · 로그인 200 · 로그아웃 204 · 중복 가입 422 · 로그인 실패 문구는 두 경우 완전히 동일. 로그인 없이 자료 화면 주소를 열면 로그인 화면만 보이고, 서버도 401로 거절한다. T06 자료 이관은 still_null=0(계획 5건 전부)로 확인했고, 배포 사이트에서 UI 클릭으로 14개 항목을 재확인했다.

카드 2 — 비밀번호를 어떻게 맡아 두는지 보이기

저장은 전부 Supabase Auth(GoTrue)에 위임했고 앱 코드는 비밀번호를 직접 해싱·저장하지 않는다. 실제 저장 값은 $2a$10$… — bcrypt(cost 10)이고 입력한 글자는 어디에도 보이지 않는다. 같은 비밀번호로 만든 두 계정의 저장 값이 서로 다름을 대조로 확인했다(salt가 다르기 때문). 수집한 모든 요청/응답을 실제 비밀번호 문자열로 grep해 원문이 전무함을 확인했다.

카드 3 — 들어온 사람을 어떻게 기억하는지 보이기

JWT access token(alg: ES256, 비대칭키) + refresh token. 만료는 expires_in=3600(1시간)으로, JWT payload의 exp/iat를 직접 디코드해 확인했다. 토큰은 URL에 실리지 않고 Authorization 헤더로만 전달된다. 같은 주소·같은 방식으로 로그아웃 전/후를 비교했고, refresh token은 즉시 거절되지만 access token은 만료 전까지 통한다는 점을 ⑥에 적었다. 이 프로젝트는 ES256이라 공유 비밀키 자체가 없는 구조이며, 저장소 전체 grep으로 클라이언트 코드·배포 파일·Git 이력에 비밀키가 없음을 확인했다.

카드 4 — 남의 자료가 안 열리는 것을 보이기

계정 두 개를 만들어 각각 자료를 넣고 양방향으로 교차 접근을 시도했다. 비밀번호는 이 문서 어디에도 적지 않았다. 읽기·수정·삭제는 양방향 모두 무효(200+빈 배열, 상대 자료의 제목·건수 실제 대조로 변경 없음 확인), 소유권 위조와 교차 INSERT는 403 42501, 주소에 남의 계정 id를 필터로 넣어도 빈 배열, complete_todo RPC로 남의 할 일을 완료 처리하려 해도 newly_completed: false, 비로그인 직접 요청은 401. 목록에는 본인 자료만 나온다. 거절을 만드는 소스는 migration-t07-auth.sql STEP 6(RLS 정책)·STEP 8(RPC 소유자 조건)이다.

읽기·수정·삭제가 설계 의도였던 403이 아니라 200+빈 배열로 막히는 이유까지 SQL로 규명해 ⑥에 적었다 — 응답 코드를 의도대로 꾸미지 않고 실제 관측값을 그대로 남겼다.

③ AI 제안을 따르지 않은 일 — 중복된 실행기록을 지워 화면 숫자를 맞추자는 제안 대신, 1일차에 정해 둔 규칙(중복은 최근 1건)을 지키고 60분 차이를 근거로 남겼다. 미완료 할 일을 억지로 완료 처리하지 않은 것도 같은 이유다.
